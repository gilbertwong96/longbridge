# v0.3.0 benchmark report

Local microbenchmarks of the SDK's message and framing paths, comparing
`v0.2.1` (protox 2.0.9) with `v0.3.0` (protox 2.1.0). No network access: every
workload runs against in-memory fixtures, so these numbers describe the CPU cost
of the generated encoders/decoders and the wire framer, not a Longbridge round
trip.

## What differs between the two trees

v0.3.0 moves protox 2.0.9 → 2.1.0 and regenerates `lib/longbridge/_protos.ex`.
The `.proto` sources are byte-identical in both trees, so any difference below
comes from the generated code and the protox runtime, never from a schema
change.

## Method

- `v0.2.1` was checked out in a git worktree; `v0.3.0` was the release commit.
  Both ran on the same machine and toolchain: Elixir 1.20.4, Erlang/OTP 29.0.5,
  10 schedulers.
- `scripts/bench_proto.exs` (standard library only — no benchmark dependency)
  ran **three times per tree, interleaved**.
- Each workload warms up, then auto-calibrates a batch size large enough to take
  at least 20 ms, then reports the **median of 7 samples** of that batch.
- Reported per operation:
  - **time** — wall clock via `:timer.tc/1`
  - **reductions** — via `Process.info(self(), :reductions)`
  - **allocation** — words reclaimed per operation, via
    `:erlang.statistics(:garbage_collection)` around a full collection
- Every workload reports a checksum of the value it produced. **All six runs
  produced identical checksums for all eight workloads**, so both trees encoded
  and decoded byte-identical payloads.

Reductions and allocation volume are deterministic for a given workload and are
therefore the trustworthy signal here. Wall time is a median on a laptop that
was also doing other work, so treat it as indicative.

## Reading the numbers

- **Encoding: 13–23% faster, 29–37% fewer reductions, 27–46% less allocation.**
- **Decoding: 37–39% faster, 60–70% fewer reductions, 31–46% less allocation.**
- The last three rows are the control group. `Header.pack + unpack` and both
  `Protocol.pack + unpack` round trips never touch protobuf code, and their
  reductions and allocation are *identical* between the trees (−0.0% on every
  one), with wall time inside run-to-run variance. That is what this harness
  looks like when the code under it has not changed — which is what makes the
  deltas above credible rather than machine drift.
- The gzip round trip's +2.6% is noise, not a regression: identical reductions
  and allocation mean it did exactly the same work, and the per-run samples
  overlap (`5002, 5102, 5370` vs `5236, 5270, 5150` ns/op).
- The decode gains exceed the protox release notes' claim (~30% less CPU, ~60%
  fewer reductions); the encode gains land near the claimed ~9% CPU / ~37%
  reductions in reductions terms, and better in wall-clock terms. Absolute
  numbers are specific to these fixtures and this machine.

## Reproducing

```sh
# candidate tree
mix run scripts/bench_proto.exs > /tmp/bench-new.json

# baseline tree
git worktree add --detach /tmp/lb-baseline v0.2.1
cp scripts/bench_proto.exs /tmp/lb-baseline/scripts/
cd /tmp/lb-baseline && mix deps.get && mix run scripts/bench_proto.exs > /tmp/bench-old.json

# side by side
jq -r '.results[] | [.name, .ns_per_op, .reductions_per_op, .words_per_op] | @tsv' /tmp/bench-*.json
```

Equal `checksum` values between the two output files mean both trees ran on
identical data. Note that the first run in a fresh tree also prints dependency
compilation to stdout, so it is worth discarding and re-running before comparing.
